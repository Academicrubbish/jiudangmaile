## 生成规则

1. 云端先确定用户人设、物品、金额、场景类型、时段和变化种子。模型不接收昵称、头像、用户编号、邀请凭证或转存记录。
2. 模型只返回标题、正文、订阅梗概、按钮、原样金额与主题标识。正文采用真实生活叙事，商品使用普通名称，购买理由可以荒诞；消费虚构性由页面和消息末行提示，不在每段故事重复解释。输出限定 JSON、长度、金额一致、物品一致；拦截明显的倒霉、疾病、冲突、道德施压、到账谎称和链接。
3. 通过格式检查后，再发起独立语义复核。复核失败、超时或不可用均不发布该候选；不使用生成结果自行声称的“已审核”。
4. 保存最近七天、最多三十件故事；生成时传入最多十件历史正文，优先包含最近五件同商品故事，并避开最近六次创作角度。独立复核比较购买诱因和包袱；程序比较主题与文本，替换商品名称仍复用原故事也会被拦截。发布时在事务内再次核对最新历史。
5. 成功或兜底都写入事件快照。已展示结果不被迟到响应改写；请客事件和公开邀请理由同步保存。

首次与主动场景的 AI 等待预算默认 **15 秒**，定时预生成默认 **40 秒**，不含数据库等其他耗时。同一次前台请求内的多条故事共用 22 秒生成截止时间，为 30 秒云函数留下数据保存时间；后台按剩余运行时间决定是否处理下一个用户，为 120 秒云函数留出余量。仍使用已配置的模型，不用更弱模型静默替代。

每用户每天默认：**故事 40 次模型请求、请客留言 20 次模型请求**。写作、独立复核、失败重试都计入各自用途；正常无重试时分别约可生成 20 条故事、10 批留言。所有用途共同受每天 2000 次全局上限约束。三种上限均可配置；个人用途上限可设置 0–200，不再强制限制为 6。达到上限后仍可以用轮换备用文案继续玩，不影响转存金额规则。

新配置字段为 `maxSceneCallsPerUserDay`、`maxGiftCallsPerUserDay`。旧的共享默认 `maxCallsPerUserDay: 6` 自动迁移为 40/20；旧字段为 0 时继续关闭两类模型调用，其他显式旧数值保留为故事上限，新增字段优先。旧当天调用记录保守计入故事已用次数，不清零全局记录；新的 `sceneCalls`、`giftCalls` 分开累计。

生成记录保存模式、提示词版本、模型名称、耗时、主题、创作角度、正文哈希和 `fallbackReason`。失败审计仅保存有限原因代码，不存请求头、Key 或供应商原始响应。完整提示词在公共模块的 `prompts.js`。

## 剧情口味

入口：首页底部「我的」 → 习惯与剧情口味；首次设置也能选择。默认“各来一半”，修改后保存到用户的 `preferences.storyTaste`。旧数据没有该字段时自动使用 balanced；旧客户端仅改金额和习惯时保留已有口味。

| 口味 | 值 | 用户习惯 / 生活随机场景 |
| --- | --- | --- |
| 贴近我的习惯 | familiar | 80% / 20% |
| 各来一半 | balanced | 50% / 50% |
| 多来点意外 | adventurous | 20% / 80% |

只控制系统自动事件，主动消费和请客使用独立商品库，支持临时自定义商品与本次金额，不受已选习惯限制。服务端维护跨天比例余额，每个已推出事件只计一次，未到期草稿、刷新、取消草稿、主动消费均不计入。修改口味保留余额和当天已用预算，不会重置生成次数；当前未处理随机事件会跳过，未到期草稿取消，后续按新口味安排。

生活随机场景目前从文具、零食、咖啡、小摆件、抱枕、杯子六类普通商品中选题，AI 自由写具体购买理由，不强行回到用户的奶茶习惯。烟、酒、槟榔不进入这个随机题材池。已经作为自定义习惯选中的同名题材不重复计作自由场景。

两类场景都有合适候选时，长期事件数量比例准确；每天最多两件，单日不保证对应比例。每类会尽量避开上一件商品。若某一类没有预算可安排的商品，则使用另一类，不为了比例突破金额范围；两类都不可安排就跳过。自由场景单次 5–30 元，也受每日自动预算限制。

规则在 `story-flavor.js`，新字段由云函数写入私有集合，无需新增集合或索引。用户保存的习惯区间不影响自由场景的价格区间，二者共同受自动事件每日总额约束。

## 随机事件

- 每天按北京时间保存一次计划，正常可用时段内至少安排一个候选；自动金额预算低于 10 元安排一件，其余可安排两件，仍受可用商品金额和剩余时段限制。主动消费不受此限制。
- 首次打开时，已到时段的随机事件会现场补齐并显示未读卡片；修改设置不清零已推出数量或金额。
- 95% 的候选时间取自 08:00–21:00，5% 取自 07:00–08:00 或 21:00–22:00。所选时段已过时，改用当天剩余可用时段，避免首个候选随机落空；后续事件仍至少间隔三小时。当日首件因任务延迟超过一小时也会补齐，免打扰时段仍不发。
- 未来事件提前十五分钟准备，在到期前不展示、不扣自动预算；到期重新检查剩余自动预算、人设和未处理随机事件，再决定是否展示。
- 主动消费、请客及真实转存确认都不占自动预算，也不替换未来随机事件；已推出随机事件在跳过、确认或撤销后均不退还自动预算。
- 22:00–07:00 不自动生成或提醒，夜间主动玩法仍可使用。
- 已开启提醒且当前模板仍有授权次数时，持续按天安排；没有可用提醒授权的用户，三个自然日未打开后暂停新任务。定时器自身不会刷新用户活跃时间。
- 应用前台每九十秒更新一次在线状态，避免人在使用时再收到外部提醒。仍未读且有授权的事件会每五分钟再次检查，离开前台后可补发；读取、处理或暂停后不再补发。凭据临时不可用也会再次检查。

每个选中习惯保存名称及每次最低／最高金额（整数分）。主动事件按用户填写的本次金额创建，推荐金额范围不限制主动消费；习惯来源的随机事件只选择最低金额不超剩余预算的习惯，并在预算允许的区间内取值。低于最低金额则跳过，绝不强行压价。事件保存当时的物品和价格快照，自定义习惯改名或删除不改变旧小票。

进入首页和前台轮询不会清除未读；主动拆开、打开详情或接受时才记录 `seenAt`。随机事件与当前主动事件分别保存，互不遮盖。已读随机事件不会再尝试发送微信提醒。

准备时间与消费时段分开，模型按事件的到期时段写作。云端任务重跑不会创建第二份同一计划事件。

服务端按用户和当前模板保存 `subscriptionCredits` 本地估算。每个有效 accept 加一；授权意图 15 分钟有效、绑定模板与暂停版本、消费后旋转，重复请求返回原结果，不重复计数。旧布尔许可按当前模板迁移为一次。客户端持久保存待同步的授权结果，断网后重试同一结果，不再调用微信申请。服务器保存的是客户端报告的意愿，不能独立证明微信剩余额度；实际发送以微信结果为准。

发送前检查时段、用户活跃、事件有效、是否暂停、是否有提醒意愿与该事件是否已尝试。取消按天的一次上限，按用户和事件去重，同一天多个新事件可分别提醒，每条各消耗一次授权。升级时识别旧按天记录，只阻止其对应事件重发，不阻止当天新事件。返回 accepted 只表示接口受理，不等于已送达或已阅读；状态未知和崩溃遗留的 sending 记录均不重复发送。

产品目标是每天至少一次提醒机会，而非每天至多一次。无可用商品预算、用户已读或已处理、已暂停、授权不足及微信接口异常时，不保证实际收到一条消息，也不重复发送同一事件凑数。

暂停会阻止尚未发出的后续请求；已经向微信发起的请求不能由本程序撤回。

凭据接口依据：[uni-open-bridge 官方说明](https://doc.dcloud.net.cn/uniCloud/uni-open-bridge)。微信官方订阅文档在本次抓取中不可读，发送接口与配置仍须结合账号后台和实际返回值验证，代码不承诺模板资格或长期订阅能力。

## 验证时观察什么

先验证开场和主动事件：在云数据库查看事件的 generation.mode 是否为 ai，模型是否为 glm-5.2，正文和金额是否匹配。若使用了兜底，可查看 jdml-ai-audit 中的原因代码；HTTP 类错误需要在智谱控制台核对权限与账号状态，不能靠反复刷新制造新请求。

然后观察 nextJobAt 和当天 plan：预先生成的事件应为 planned，到期后才为 offered；主动消费不占用或替换随机事件计划，修改习惯后，不再适用的草稿会被取消。

最后用获准模板验证订阅请求和 jdml-notices 状态。真实模型的二百条内容评测、实际延迟、云数据库并发和真机体验尚待验证，本轮本地测试不能代替这些结果。


### 累计订阅真机验证

1. 同步上传 `jdml-users.schema.json`、`jdml-core`、`jdml-api` 和 `jdml-worker`，重新编译前端；不要只更新前端，避免新旧协议混用。

### 提醒面板旧接口兼容

### 真实生活叙事修复 5.1

提示词版本为 `jdml-scene-5.1`。生成及独立复核均明确拒绝空气商品、假装点单等玩法解释；发布前还对标题、正文、梗概和按钮执行独立风格检查，失败记录 `SCENE_STYLE`，重试后仍不合格则采用审定备用故事。自然环境的空气以及空气净化器、空气凤梨等真实商品不因“空气”二字被拦截。模型输入及备用故事中的内置商品使用普通名称，避免旧快照的“空气奶茶”再次污染输出。

### 主动商品库与临时消费

首页“花一笔”“请朋友”共用 `bootstrap.shopOptions` 返回的商品库，包含启用的内置商品、六类生活商品及用户已保存的自定义习惯。`capabilities.manualShop` 表示服务端支持本次金额及临时商品；旧云函数缺少该能力时，前端提示商品库尚未准备好，不能把用户填写金额交给会忽略它的旧接口。

主动创建传 `habit + amount`，或传 `customItem: { name } + amount`，二者不能混用。金额为整数分，单次 1–1000 元；临时名称 1–12 字，沿用现有名称校验。服务端分配稳定的临时物品编号并保存事件快照，临时商品不写入推荐偏好，不修改剧情比例余额，也不消耗每日随机预算。自定义商品可请朋友，仍是一卡一人、24 小时有效。

抽屉使用独立遮罩关闭，内容区及商品按钮阻止点击冒泡，选择商品和编辑输入框不应关闭抽屉。生成中禁止关闭和重复提交；请求失败保留所填内容。

部署 `jdml-core` 公共模块（新增 shop.js）及引用它的 `jdml-api`、`jdml-worker`，重新编译前端；本轮不新增数据库集合或索引。真机验证：只选奶茶人设，分别买咖啡、填写烤红薯和金额、请朋友一张电影票，检查选择时抽屉保持打开、金额和商品快照一致，推荐设置与随机预算保持原值。

- 已生成的故事、小票与分享卡继续保存原文，不因升级或刷新改写；请创建一条新事件验证新版，不需要清空数据库。

部署：重新上传公共模块 `jdml-core`（包含新的 `scene-library.js`、提示词和配置），再更新依赖它的 `jdml-api`、`jdml-worker`。本地私密配置的调用次数与等待预算已经更新，上传时需确认云端同步使用这些数值；密钥与模型未变。无需新增集合、清空数据或修改前端。

线上排查新事件的 `generation`：`promptVersion` 应为 `jdml-scene-6.0`；`mode=ai` 是审核通过的模型结果，`mode=fallback` 是备用库结果。`fallbackReason` 和 `jdml-ai-audit.reason` 可帮助区分：

| 原因 | 含义 |
| --- | --- |
| `AI_SCENE_QUOTA` / `AI_GIFT_QUOTA` | 对应用途的个人请求额度用尽 |
| `AI_GLOBAL_QUOTA` | 全局额度用尽 |
| `AI_DISABLED` | 模型未开启或配置未就绪 |
| `AI_TIMEOUT` / `TIMEOUT` | 生成时间用尽或网络请求超时 |
| `SCENE_DUPLICATE` | 与最近文案重复 |
| `SEMANTIC_REJECTED` | 独立复核未通过 |
| `SCENE_STYLE` / `SCENE_CONTENT` / `SCENE_LENGTH` | 文案风格、内容或长度检查未通过 |
| `GENERATION_BUSY` | 同一事件的生成正在被另一请求处理，先固定备用结果 |
| `READ_FALLBACK` / `EVENT_CLOSED` | 只读兜底或事件状态已不适合生成 |

验证建议：连续创建六条丑猫抱枕新事件，在模型关闭或额度耗尽时确认六条备用剧情不同；第七条才开始轮换。打开同一条小票，正文应保持不变。模型启用时观察历史上下文和回退原因，分别用尽故事与留言额度，确认另一类仍有独立额度。
